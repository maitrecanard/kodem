## Architecture
- Monolith with TWO public surfaces coexisting:
  1. Audit product (SEO/security audits, monitoring, payments) — original site.
  2. Vitrine "dispositifs logiciels connectés sur site" (photomatons, écrans Raspberry, signalétique) — added 2026-06-30, ADDITIVE.
- Inertia flow: `Inertia::render('Public/PageName', ['meta'=>['title','description'], ...props])`. PublicLayout.jsx consumes meta.title/description only (omit `keywords` on new pages — charter §8 forbids keyword stuffing).
- Vitrine content is FILE-BASED (no DB/Eloquent): `content/*.json` loaded by `App\Services\VitrineContent` (static, mirrors `App\Services\PrestationCatalog`).

## Animation (système CSS-only, depuis 2026-07-30, v1.16.0)
- **Zéro JavaScript d'animation, et ça doit le rester.** Aucune lib (framer-motion/gsap/aos/react-spring) n'est installée ; `MotionGuardTest` échoue si l'une apparaît dans `package.json`. Tout passe par la feuille compilée par Vite — jamais de `<style>` inline ni de `style={{animation}}` (ça s'appuierait sur la dette `'unsafe-inline'` de la CSP).
- **Pourquoi les animations d'entrée rejouent à chaque navigation sans JS** : `resources/js/app.jsx:23` monte le client via `createRoot().render()` (la branche `hydrateRoot` est gardée par `import.meta.env.SSR`), et Inertia remonte le composant de page avec une **clé neuve à chaque visite** → nœuds DOM neufs → les `@keyframes` redémarrent. Corollaire utile : une visite `preserveState: true` (erreur de validation de formulaire) ne remonte pas, donc pas de re-animation parasite.
- **Budget de mouvement, source unique** : `:root` de `resources/css/app.css` (`--kodem-dur-2: 220ms`, `--kodem-dur-3: 420ms`, `--kodem-ease`, `--kodem-ease-io`, `--kodem-rise: 8px`). Aucune valeur de durée en dur ailleurs — `test_motion_values_come_from_tokens` le verrouille. Primitives dans `tailwind.config.js` : `animate-kodem-fade` / `-rise` / `-slide`. Motifs composés dans `app.css` : `.kodem-card` (lift -2px), `.kodem-link` (filet `::after` en scaleX).
- **`animate-kodem-slide` (translation SEULE, sans opacité) est obligatoire sur les pages sans bannière.** Mesuré au Lighthouse le 2026-07-30 sur `/contact`, à FCP constant (2,6 s) : `kodem-rise` → **LCP 4,2 s** ; sans animation → **3,6 s** ; `kodem-slide` → **3,6 s**. Chrome ne retient pas comme candidat LCP un élément peint à `opacity: 0` ; un élément seulement translaté reste peint donc éligible. **Ne jamais « simplifier » en remettant `rise` sur une page sans bannière** — `test_banner_less_pages_use_opacity_free_entry_animation` passe au rouge.
- **Trois exclusions non négociables**, chacune tenue par un test : aucun `<h1>` de la surface publique animé (ni directement, ni via un ancêtre) ; `<h1>` et `<img>` de `Banner.jsx` nus (élément LCP mesuré de `/` et `/realisations` = l'`<img>` de bannière) ; aucun `animate-*` dans `PublicLayout.jsx` (header collant + footer remontent à chaque navigation → flash de chrome ; et une `transform` sur un ancêtre casse `position: sticky`).
- **Ne jamais mettre l'utilitaire Tailwind `transition` à côté de `kodem-card`** : `.transition` est émis dans `@layer utilities`, donc APRÈS `.kodem-card` (`@layer components`) ; à spécificité égale il gagne et écrase les tokens (150 ms au lieu de 220 ms). `.kodem-card` déclare déjà sa transition.
- **Reveal au scroll = `.kodem-reveal`** (`animation-timeline: view()` + `animation-range: entry 0% cover 40%`, courbe `linear`, amplitude `--kodem-reveal-rise: 32px`), posé sur les sections de second niveau de 11 pages longues.
- **Les trois réglages du reveal ont été trouvés par MESURE, ne pas les « simplifier »** : (a) `animation-duration` est **sans effet** sur une timeline `view()` — seule `animation-range` gouverne la vitesse perçue ; (b) une courbe ease-out y est **doublement amortie** et écrase la fin de course, d'où `linear` (c'est le geste de scroll qui porte l'accélération) ; (c) `cover 25%` terminait la révélation dans les 250 px du BAS du viewport — opacité 0,99 alors que la section était encore à 550 px du haut de l'écran, donc invisible en pratique. Avec `cover 40%` + `linear`, la progression est étalée sur toute la hauteur d'écran (0,06 en bas → 0,47-0,89 au milieu → 1 en haut), c'est-à-dire là où l'œil se trouve réellement.
- **Sonde de mesure du reveal** (à réutiliser) : Playwright + `window.scrollTo()` **suivi de deux `requestAnimationFrame`** avant de lire `getComputedStyle`. Sans cette attente de frame, Chrome renvoie une valeur périmée et la courbe mesurée est un escalier en marches — piège rencontré le 2026-07-30, la première sonde était fausse. Encapsulé dans `@supports (animation-timeline: view())` **et** `@media (prefers-reduced-motion: no-preference)` — hors de ce bloc la classe n'a AUCUNE règle, donc aucun état masqué. Support vérifié sur Chrome 150 (`view()` + `animation-range` = true) et comportement mesuré au navigateur : hors écran opacity 0 / translateY(14px), à mi-révélation 0,46 / 7,5px, dans le viewport 1 / 0.
- **Piège : `animation-delay` est SANS EFFET sur une timeline `view()`.** Donc `.kodem-stagger` (cascade, timeline du document, réservée aux grilles du PREMIER écran) et `.kodem-reveal` ne doivent jamais coexister sur le même élément — `test_stagger_and_reveal_are_never_combined` l'interdit. Pour une cascade sous le pli, il faudrait varier `animation-range` par `:nth-child`, pas `animation-delay`.
- **Ne jamais poser `.kodem-reveal` sur le premier bloc d'une page** (déjà dans le viewport au chargement → opacité partielle possible → risque de devenir l'élément LCP), ni l'imbriquer dans un autre `.kodem-reveal` (`test_kodem_reveal_is_never_nested`).
- **Impossible en CSS seul, ne pas re-explorer** : les transitions inter-pages type View Transition (`@view-transition` est **cross-document** ; Inertia navigue en same-document → exigerait `document.startViewTransition()`).
- **Leçon de dosage (2026-07-30)** : une première passe « premier écran uniquement » à 8 px a produit un site que l'utilisateur a perçu comme **totalement non animé** — deux animations jouées au chargement, tout le reste inerte au défilement. Ce n'était pas un bug mais un problème de dosage. Retenir : l'animation d'entrée seule ne suffit jamais à donner l'impression d'un site animé, c'est le reveal au scroll qui le fait ; et 8 px est sous le seuil de perception (14 px = « net mais sobre », arbitrage utilisateur).
- CLS résiduel de 0,025 mesuré sur `/audits/premium` : **imputable au chargement des polices Space Grotesk depuis fonts.bunny.net** (reflow de substitution), pas aux animations. Préexistant. Les pages animées sont à CLS 0.
- Outillage de mesure disponible localement : Chrome (`/usr/bin/google-chrome`) + `npx lighthouse@12 <url> --chrome-flags="--headless=new --no-sandbox"`. Un serveur de dev tourne sur `127.0.0.1:8000` et sert les assets **buildés** (pas de `public/hot`). `PageSpeedClient`/`AuditRunner` appellent l'API Google et ne peuvent donc PAS mesurer localhost.

## Security Notes
- `app/Http/Middleware/SecureHeaders.php` — HSTS **and** `upgrade-insecure-requests` are both gated on `$isSecureContext = $request->secure() || app()->environment('production')`. Never emit `upgrade-insecure-requests` unconditionally: on a plain-HTTP dev server it silently breaks every non-GET request. `TrustProxies` (bootstrap/app.php, 127.0.0.1 + X-Forwarded-Proto) makes `secure()` true behind a TLS reverse proxy — verified by test.
- Never flash `$e->getMessage()` or user-controlled content into `success`/`error`: the shared `flash` prop is serialised into the `data-page` attribute of the HTML.
- KNOWN PREEXISTING (not yet fixed): `style-src` carries `'unsafe-inline'` (MEDIUM); `HandleInertiaRequests` shares the whole `User` model including the raw auto-increment `id` (should expose a uuid or a whitelist).
- JSON-LD XSS-safe: single hardened json_encode on the FINAL merged graph; never merge a node after encoding, never a second un-flagged encode.
- Slug params are opaque content strings used only for in-memory `firstWhere` lookups — never concatenated into a filesystem path. VitrineContent reads fixed `base_path('content/xxx.json')` literals only.
- Global rule: any user identifier in the frontend MUST be UUID/opaque, never a raw DB id. Vitrine exposes only content slugs (photomaton/ecran-raspberry). Existing entity routes already use {audit:uuid}/{subscription:token}.
- `content/testimonials.json` now holds real people's names + employers. Keep it to {citation, nom, fonction, structure, photo} — never import email/phone/profile URL/remote avatar (a hotlinked LinkedIn/Malt avatar would also leak visitors' Referer). `tests/Unit/VitrineContentTest.php` asserts the exact key set as a PII guard.
- Case visuals must be screened before import: never publish a third-party screenshot/logo that names a client the case itself doesn't name. Always convert with `-strip` (EXIF/GPS).
- No secrets/PII in content/*.json or new code.
- PREEXISTING DEBT (charter HIGH, out of scope so far): 4 × `@file_get_contents` in `app/Services/VitrineContent.php` (~L28/44/70/98) silently swallow a missing/unreadable/malformed content file → empty section, no log. Remediation: `is_readable()` check + `json_decode(..., JSON_THROW_ON_ERROR)` in a try/catch that calls `Log::error(...)`.
